# SMC COM9026 (ARCNET LANC): emulator spec for the ICON

Source: SMC COM9026 datasheet, 12 scanned pages, printed pages 213 to 224 (`/Users/dani/Downloads/COM9026.PDF`).
Cross-checked against the ICON boot ROM (`firmware/ICON1/icon1_rom_combined.bin`; offsets below are **file offsets**).
Notation: `[DS p.N]` is a printed datasheet page number. `[ROM xxxx]` is a ROM file offset. **Inference** marks anything that is not stated in the datasheet.

---

## 1. Bus interface (what the CPU sees)

The chip has a multiplexed 8-bit bus (AD7–AD0) and drives A10–A8 to an external 2K×8 RAM. The CPU sees two separate things:

* **Four I/O "locations"** (the datasheet says "4 I/O locations", but only three are used). They are selected by IOREQ, **AD0** and R/W [DS p.222]:

  | AD0 | R/W | Function |
  |---|---|---|
  | 0 | write | write INTERRUPT MASK |
  | 0 | read | read STATUS |
  | 1 | write | write COMMAND |
  | 1 | read | "reserved for future use" |

  On the ICON, CPU A1 is wired to chip AD0, so **F880 = status (read) / mask (write)** and **F882 = command (write)**. A read of F882 is undefined. **Inference:** return 0xFF.
* **External buffer RAM** (MREQ cycles). The chip only arbitrates access to it; the RAM is a plain SRAM. On the ICON, RAM byte *n* (0..0x7FF) is at **D8000 + 2n**. The odd addresses D8001, D8003, … are not connected to this RAM. **Inference:** odd bytes read as open bus (0xFF). This matters at [ROM 1671] (see §8).
* **Pages.** "the RAM buffer can be as large as 2K byte locations providing four pages at a maximum of 512 bytes per page" [DS p.219]. A10–A9 = page number *nn* from the last ENABLE RECEIVE / ENABLE TRANSMIT [DS p.215]. So page *nn* starts at RAM byte `nn*0x200`. On the ICON, page 0 is at D8000, page 1 at **D8400**, page 2 at D8800 and page 3 at D8C00. When long packets are not enabled, only the first 256 bytes of a page are used (A8 = 0).
* **WAIT.** CPU accesses are stretched by at most 1.3 µs while the chip uses the RAM [DS p.221]. An emulator can ignore this; treat the RAM as true dual-port.
* **INTR** (pin 29) goes to **PPI A port C bit 5** (F985 & 0x20) on the ICON. INTR = `POR | (status & mask & 0x85)` (see §2).
* **Node ID input.** The chip reads its ID **serially**: it pulses IDLD to load an external shift register (an LS166 in the datasheet's Figure 20), then shifts IDDAT in MSB first [DS p.215]. On the ICON, the ROM writes the ID to PPI B port A (**FAC1**). **Inference:** that port drives the parallel inputs of the shift register. The chip samples the ID right after POR is released ("after reading its ID from the external shift register") [DS p.221]. The flowchart also reads it again on every reconfiguration-timer timeout. A footnote says: *"The ID set by the external switches is continually sampled during COM 9026 operation"* [DS p.218]. **Emulator:** latch FAC1 when reset is released, and also re-read it on a reconfiguration.
* **Reset.** The POR pin (40) is active low. On the ICON, reset is asserted while PPI A port B (F983) **bit 1 = 1**. The ROM sets bit 1, writes the ID to FAC1, waits about 1000 loop iterations, clears bit 1, then waits about 1000 more before checking RAM [ROM 15BD–15F0]. The datasheet asks for POR to be held for ≥100 ms; the ICON holds it much more briefly, so don't enforce the minimum.
* **ET1/ET2** (pins 3 and 1) select the timeout set (Table 1). They are reflected in status bits 5 and 6. ICON strapping is unknown, so the ROM masks those bits out. **Recommendation:** ET1 = ET2 = 1, which gives the standard 78 µs / 840 ms timeouts and status bits 6:5 = 11.
* **ECHO** (pin 30): when low, the chip "will re-transmit all messages of length less than 254 bytes", a diagnostic loop. It is tied high in normal use, so ignore it. TEST1/TEST2 are grounded.

## 2. Registers

### STATUS (read, F880) [DS p.222–223]

| Bit | Name | Meaning / set / clear |
|---|---|---|
| 7 | **RI** Receiver Inhibited | **1 = no receive enabled / a packet has arrived.** *"indicates that a packet has been deposited into the RAM buffer page nn as specified by the last ENABLE RECEIVE TO PAGE nn command … No messages will be received until an ENABLE RECEIVE TO PAGE nn command is issued. After any message is received, the receiver is automatically inhibited by setting this bit to a logic one."* **Set by:** POR; successful reception (after a good CRC and length, with the ACK sent if the packet was not a broadcast); DISABLE RECEIVER (takes effect the next time this node gets the token, if no reception is in progress). **Cleared by:** ENABLE RECEIVE (`b00nn100`), immediately. Maskable (mask bit 7). |
| 6 | ETS2 | Level of the ET2 pin. Not affected by POR. Never interrupts. |
| 5 | ETS1 | Level of the ET1 pin. Not affected by POR. Never interrupts. |
| 4 | **POR** | *"indicates that the COM 9026 has received an active signal on the POR input (pin 40). The setting of this bit will cause a nonmaskable interrupt via INTR."* **Set by:** reset. **Cleared by:** CLEAR FLAGS with p = 1 (`0x0E` or `0x1E`). |
| 3 | TEST | *"will be a logic zero under any normal operating conditions."* Always 0. |
| 2 | **RECON** | *"indicates that the reconfiguration timer has timed out because the RX input was idle for 78.2 microseconds."* (This wording mixes two timers; see §8.) **Inference, which agrees with the ROM self-test:** it is set whenever a network reconfiguration happens: after this node's power-on burst, after another node's burst, or after this node's 840 ms no-token timeout. **Cleared by:** CLEAR FLAGS with r = 1 (`0x16` or `0x1E`); *"reset low during a CLEAR FLAGS command"*. It is **not** cleared by POR's own reset (POR sets RECON = 0, but the burst sets it again a few ms later). Maskable (mask bit 2). |
| 1 | **TMA** Transmit Message Acknowledged | *"the packet transmitted as a result of an ENABLE TRANSMIT FROM PAGE nn command has been positively acknowledged. This bit should only be considered valid after the TA bit (bit 0) is set. Broadcast mesages are never acknowledged."* **Cleared by:** ENABLE TRANSMIT and POR. **Set by:** receipt of the ACK for the data packet. Never interrupts. |
| 0 | **TA** Transmitter Available | *"set at the conclusion of a ENABLE TRANSMIT FROM PAGE nn command or upon the execution of a DISABLE TRANSMITTER command."* **Set by:** POR; completion of a transmit (see §6 for the exact cases); DISABLE TRANSMITTER, at the next token. **Cleared by:** ENABLE TRANSMIT. Maskable (mask bit 0). |

**Reset value** [DS p.221], verbatim: *"BIT 7 (RI) set to a logic "1". BIT 6 (ETS2) not affected. BIT 5 (ETS1) not affected. BIT 4 (POR) set to a logic "1". BIT 3 (TEST) set to a logic "0". BIT 2 (RECON) set to a logic "0". BIT 1 (TMA) set to a logic "0". BIT 0 (TA) set to a logic "1"."* That is `0x91 | ETS bits`, which is exactly what the ROM's `status & 0x91 == 0x91` checks [ROM 1604].

### INTERRUPT MASK (write, F880) [DS p.223]

The mask bits use the same positions as the status bits: **bit 7 RI, bit 2 RECON, bit 0 TA**. The other bits are "XXX".
*"The setting of the TMA, EST1, and EST2 status bits will never cause an interrupt. The POR status bit will cause a non-maskable interrupt regardless of the value of the corresponding MASK register bit."*

`INTR = POR || (RI && m7) || (RECON && m2) || (TA && m0)`. INTR is level-triggered. To drop it: CLEAR FLAGS (for POR or RECON), or clear the mask bit (for TA or RI, since those status bits are cleared only by issuing a new command). The mask is reset to 0 by POR: *"the interrupt mask register is reset (no maskable interrupts enabled)"* [DS p.221]. The mask is write-only.

## 3. Commands (write, F882) [DS p.223]

| Encoding | Name | Effect |
|---|---|---|
| `00000000` | reserved | — |
| `0x01` `00000001` | **DISABLE TRANSMITTER** | *"will cancel any pending transmit command (transmission has not yet started) when the COM 9026 next receives the token. This command will set the TA … bit when the token is received."* If a transmit has already started, it finishes normally. |
| `0x02` `00000010` | **DISABLE RECEIVER** | *"will cancel any pending receive command. If the COM 9026 is not yet receiving a packet, the RI … bit will be set the next time the token is received. If packet reception is already underway, reception will run to its normal conclusion."* |
| `000nn011` = `0x03 / 0x0B / 0x13 / 0x1B` | **ENABLE TRANSMIT FROM PAGE nn** | Sets TX page = nn, **TA = 0, TMA = 0** immediately, and arms a transmit for the next time this node holds the token. *"The TA bit is set to a logic one upon completion of the transmit sequence. The TMA bit will have been set by this time if the COM 9026 has received an acknowledgement from the destination COM 9026 … the TMA bit is not a guarantee of proper destination reception."* |
| `b00nn100` = `0x04 / 0x0C / 0x14 / 0x1C`, plus `0x80` for broadcast | **ENABLE RECEIVE TO PAGE nn** | Sets RX page = nn, **RI = 0** immediately. *"If "b" is a logic "1", the COM 9026 will also receive broadcast transmissions. A broadcast transmission is a transmission to ID zero. The RI status bit is set to a logic one upon successful reception of a message."* One enable accepts exactly **one** packet. |
| `0000c101` = `0x05` / `0x0D` | **DEFINE CONFIGURATION** | c = 1: *"will handle short as well as long packets"*. c = 0: *"will only handle short packets (less than 254 bytes)"*. |
| `000rp110` = `0x06 / 0x0E / 0x16 / 0x1E` | **CLEAR FLAGS** | p = 1 (bit 3) clears POR. r = 1 (bit 4) clears RECON. |
| anything else | — | *"not permitted and can result in incorrect chip and or network operation."* **Inference:** ignore it. |

Bit layout: the low 3 bits are the opcode. Bits 4:3 = nn for TX and RX. Bit 7 = b (broadcast enable) for RX. Bit 3 = c for config. Bit 3 = p and bit 4 = r for CLEAR FLAGS.

ICON ROM commands, decoded:
* `0x01` disable TX, `0x02` disable RX (both used in init [ROM 12E9] and in the loader [ROM 0349]).
* `0x03` = ENABLE TRANSMIT FROM PAGE **0**.
* `0x0E` = CLEAR FLAGS, POR only. `0x1E` = CLEAR FLAGS, POR + RECON.
* `0x8C` = `1 00 01 100` = ENABLE RECEIVE TO PAGE **1** **with broadcast**.
* The ROM never issues DEFINE CONFIGURATION, so it relies on the reset default (see §8). It only ever uses short packets.

Status polls in the ROM:
* `& 0x81 == 0x81`: RI and TA both 1. The receiver and transmitter are idle after the disables [ROM 035E].
* `& 0x80 == 0`: RI cleared after 0x8C [ROM 0380].
* `& 0x01`: TA, meaning the transmit has finished [ROM 04F6].
* `& 0x03 == 3`: TA and TMA, meaning the transmit was acknowledged [ROM 0506].
* `& 0x80` set: a packet has arrived [ROM 056A].

## 4. Buffer RAM packet format [DS p.217, Figure 8]

Offsets are relative to the page base (RAM byte `nn*0x200`; CPU address `D8000 + 2*(nn*0x200 + off)`).

| Offset | Short packet (256-byte page) | Long packet (512-byte page) |
|---|---|---|
| 0 | SID | SID |
| 1 | DID | DID |
| 2 | COUNT = 256 − N | **0x00** |
| 3 | not used | COUNT = 512 − N |
| COUNT … 255 or 511 | data byte 1 … data byte N | data byte 1 … data byte N |

* **N** is the data length. The data always **ends at the last byte of the page**, and COUNT is the offset of the first data byte. *"the COM 9026 will interpret the packet as a long or short packet depending on whether the contents of buffer location 02 is zero or non zero."*
* **Short packets:** COUNT ≥ 3, so N ≤ 253 ("less than 254 bytes"). **Long packets:** require DEFINE CONFIGURATION c = 1. The general description says the maximum is "508 bytes", so COUNT ≥ 4. N = 254–256 cannot be encoded in either form; the datasheet doesn't say so explicitly.
* **On the wire:** `SOH(01) SID DID DID COUNT [COUNT2] data… CRC CRC`. A short packet has *one* COUNT character (the 2's complement of N). A long packet has `00` followed by COUNT [DS p.216]. The CRC is X^16 + X^15 + X^2 + 1.
* **SID on TX:** the datasheet doesn't say whether the chip sends buffer byte 0 or its own ID. **The ICON ROM never writes byte 0 of the TX page.** It writes DID at [1], 0xF6 at [2] and data at [F6..FF] [ROM 06B9]. So the chip **must supply its own ID as the SID**, and an emulator must send `SID = own node ID` and ignore buffer byte 0.
* **On RX**, the receiver writes the SID to byte 0 *before* it checks the DID (flowchart: SOH → RI? → "WRITE SID TO BUFFER" → DID checks). It then writes DID, COUNT(s) and data into the RX page at the same layout. **Side effect:** while receive is enabled, every packet on the wire overwrites RX page byte 0 with its SID, even when it is addressed elsewhere. The chip may also leave partial data from a packet that fails CRC or length checks. Both are harmless; the ROM only looks after RI = 1.
* **Broadcast:** set DID = 0. *"ID zero is reserved for this feature and no node on the network can be assigned ID zero … Each individual node has the ability to ignore broadcast messages by setting the most significant bit of the ENABLE RECEIVE TO PAGE nn command … to a logic zero"* [DS p.217]. A received broadcast has DID = 0 at offset 1.

## 5. Reset / power-on

While POR is asserted: status = `0x91 | ETS`, mask = 0, *"Page 00 is selected for both the receive and the transmit RAM buffer"*. Pending TX/RX are cancelled (RI = 1 and TA = 1 imply this).

After release [DS p.221]: *"After the POR signal is removed, the COM 9026 will generate an interrupt from the nonmaskable Power On Reset interrupt. The COM 9026 will start operation four CA clock cycles after the POR signal is removed. At this time, the COM 9026, after reading its ID from the external shift register, will execute two write cycles to the RAM buffer. Address 00 HEX will be written with the data D1 HEX and address 01 HEX will be written with the ID number as previously read from the external shift register. The processor may then read RAM buffer address 01 to determine the COM 9026 ID … Only if the D1 pattern appears in the RAM buffer can proper operation be assured."*

**Emulator, on reset release (t0):**
1. Latch ID = the FAC1 output value. Write RAM[0] = 0xD1 and RAM[1] = ID within a few µs (the ROM checks after about 1000 loop iterations).
2. INTR is high because of POR.
3. From the flowchart, the chip then **sends the RECONFIGURE BURST**: "eight marks and one space repeated 765 times", which is 765 × 9 × 0.4 µs ≈ **2.75 ms**. After that it goes into the reconfiguration sweep (§6).
4. About 78.2 µs after the burst ends (t0 + ~2.83 ms), **set RECON on every node on the wire**, including this one.

The ROM self-test depends on this order [ROM 15BD–16EA, error codes 31/32/33]:
1. Reset.
2. RAM[0] == D1. **Note:** the only RAM check found in the ROM is D1; a RAM[1] == ID check was not found.
3. INTR (PC5) = 1.
4. Status & 0x91 == 0x91.
5. 2K RAM pattern test.
6. Mask = 0, then `0x0E`. INTR must go **0**.
7. Mask = 01 (TA). INTR must be **1**.
8. Mask = 04 (RECON). INTR must be **1**, so RECON must already be set by now (the RAM test takes milliseconds, so ~2.8 ms is fine).
9. Mask = 80 (RI). INTR must be **1**.
10. `0x1E`, then mask = 04. INTR must be **0**.
11. Mask = 0.

## 6. Network behaviour and the recommended model

### What the datasheet says (Figure 3 flowchart, p.216–218, Table 1)

* **Line timing:** 2.5 Mbit/s, 400 ns per bit interval. Each character is 11 intervals (2 mark, 1 space, 8 data) = **4.4 µs**. The alert burst is 6 intervals (2.4 µs).
  * ITT = alert + `EOT DID DID` (≈15.6 µs). FBE = alert + `ENQ DID DID` (≈15.6 µs). ACK = alert + `86h` (≈6.8 µs). NAK = alert + `15h`.
  * A data packet takes 2.4 + 4.4 × (N + 7) µs for a short packet, or N + 8 characters for a long one.
* **Timeouts (Table 1, ET2/ET1):**

  | ET2 ET1 | Response (µs) | Idle (µs) | Reconfig (ms) |
  |---|---|---|---|
  | 1 1 | 78 | 86 | 840 |
  | 1 0 | 285 | 316 | 1680 |
  | 0 1 | 563 | 624 | 1680 |
  | 0 0 | 1130 | 1237 | 1680 |

  The text uses **74.7 µs** (response) and **78.2 µs** (idle) for the standard setting.
* **Token holder (flowchart, left side).** When it receives an ITT addressed to itself, the chip restarts its 840 ms reconfiguration timer, then:
  * **TA = 1** (nothing pending): pass the token.
  * **TA = 0, DID = 0 (broadcast):** SEND PACKET → "WAS PACKET BROADCAST?" Y → **SET TA** → pass the token. There is no FBE and no ACK, and TMA stays 0.
  * **TA = 0, DID ≠ 0:** send FBE to DID, then:
    * *No activity for 74.7 µs* (the node doesn't exist): **SET TA**, TMA = 0, pass the token.
    * **ACK**: SEND PACKET, then:
      * no activity for 74.7 µs: **SET TA** (TMA = 0).
      * ACK: **SET TMA, SET TA**.
      * anything else: pass the token *without* setting TA. The whole sequence retries at the next token.
    * **NAK** (the destination's RI = 1): pass the token, TA stays 0, and it **retries at every token rotation, indefinitely**, until the destination enables receive or the CPU issues DISABLE TRANSMITTER.
    * Other: back to the main loop.
* **Pass token:** send an ITT to NID. If there is no activity for 74.7 µs, increment NID and try again. This is how the chip learns its successor.
* **Receiver (flowchart, right side):**
  * FBE to this ID: if RI = 1, NAK; else ACK.
  * SOH:
    1. If RI = 1, ignore it.
    2. Write SID to the buffer.
    3. If DID = 0, it is accepted only if broadcast was enabled (that diamond is illegible; **inferred**). If DID = ID, accept. Otherwise drop it.
    4. Write the packet to the buffer.
    5. CRC bad → drop. Length bad → drop (for example a long packet while c = 0).
    6. DID = 0 → **SET RI** (no ACK). DID = ID → **SEND ACK**, then **SET RI**.
* **Reconfiguration** [DS p.217]:
  * A node sends a RECONFIGURE BURST when it powers on, or when its 840 ms timer expires because it hasn't received the token. The burst destroys the token.
  * When any node sees the line idle for 78.2 µs, it sets NID = ID and starts a timer of **146 µs × (255 − ID)**. The highest ID times out first and starts sending ITTs to NID = ID + 1, ID + 2, …, wrapping, until one answers. *"INVITATIONS TO TRANSMIT will be sent to all 256 possible ID's"*.
  * *"The time required to do a NETWORK RECONFIGURATION … will be in the range of 24 to 61 milliseconds."*
* **Lone node (inferred from the flowchart):** it never hears a reply to its ITTs, so it never receives the token. Its pending TX never completes (TA stays 0). It re-bursts every 840 ms, setting RECON each time. A lone ICON whose network boot is enabled therefore times out in the ROM's TA wait and reports error 57.

### Recommended simplified model (two or more nodes on one virtual wire, shared simulated clock)

State per node: `id`, `status{ri, por, recon, tma, ta}`, `mask`, `tx_page`, `rx_page`, `rx_bcast`, `long_ok` (from DEFINE CONFIGURATION), `pending_disable_tx/rx`, `in_reset`, and 2 KB `ram`.

1. **CPU writes take effect immediately:**
   * `03`-type: TA = TMA = 0; set `tx_pending`.
   * `8C`-type: RI = 0; set the RX page and broadcast flag.
   * CLEAR FLAGS / mask: immediate.
   * `01` / `02`: set a pending flag that is resolved at the node's next token visit. It is fine to resolve it at the next "token tick", or immediately if the bit is already in the target state.
2. **Wire.** The wire is "up" when at least **two** nodes are out of reset and no reconfiguration is in progress. Order the nodes by ID; the token visits them in ascending ID order, wrapping.
3. **Reconfiguration event.** This happens on any node's reset release, and every 840 ms while a node is alone.
   * The wire goes down for **T_burst = 2.75 ms**.
   * At t + 2.83 ms, set RECON on all live nodes. Raise INTR where RECON is masked in.
   * The wire comes back up at t + **~25 ms**. Anywhere in 24–61 ms is fine; the ROM is not sensitive to it.
4. **Token tick.** While the wire is up, run a token visit every **~20 µs per node** (ITT ≈ 15.6 µs plus turnaround). Coarser ticks, such as 100 µs, are acceptable. At node X's visit:
   * Resolve its pending disables (DISABLE TX → TA = 1; DISABLE RX → RI = 1).
   * If `tx_pending`, read `DID = ram[tx+1]`, `COUNT = ram[tx+2]` (or `ram[tx+3]` for a long packet if `ram[tx+2] == 0`), and the data.
   * **DID = 0:** for each other node Y with `!Y.ri && Y.rx_bcast` (and long packets allowed if needed), copy the packet into Y's RX page: `[0] = X.id`, `[1] = 0`, `[2]` (and `[3]`) = counts, and the data at the same offsets. Set `Y.ri = 1`. Then X.TA = 1 and TMA stays 0. Schedule completion at `+packet_time`.
   * **DID ≠ 0, no live node has that ID:** X.TA = 1, TMA = 0, after ~15.6 + 74.7 µs.
   * **Y.ri = 1:** NAK. Keep it pending and retry at X's next visit. This can loop forever, which is correct behaviour.
   * **Otherwise:** copy the packet into Y (`[0] = X.id`, `[1] = DID`, …), set Y.RI = 1, then X.TMA = 1 and X.TA = 1. Use the time FBE + ACK + packet + ACK ≈ `15.6 + 6.8 + (2.4 + 4.4*(N+7)) + 6.8 + ~4×12 µs turnaround`. A 10-byte request takes about 155 µs.
   * **Event order:** the destination's RAM write and RI = 1 happen *before* the sender's TMA/TA. The ACK is sent before RI is set, and TA is set after the ACK is received. Recompute INTR on both nodes.
5. **Reset release:** see §5. While a node is held in reset, it is absent from the wire, and it doesn't ACK or NAK.

## 7. Worked example: ICON ROM network boot

Two nodes are on the wire: the client, ID 0xFE (254, the factory default), and the server, ID 0xF5 (245). Their IDs come from NVRAM word 10. The server runs QNX `bootrec`.

**Power-on self-test** (`T` = the client's chip):
1. PB1 = 1 (reset) and FAC1 = FE. Then PB1 = 0.
2. T writes RAM[0] = D1 and RAM[1] = FE. Status = 0x91 (0xF1 with ET pins high). INTR = 1.
3. T sends its burst. Both nodes see RECON = 1 at about +2.8 ms, and the network reconfigures over about 25 ms. The server's QNX driver sees RECON (and an interrupt, if it has RECON masked in).
4. The ROM runs its self-test (§5). It ends with mask = 0, then `01, 02, 1E` [ROM 12E3].

**Loader** [ROM 0342–05E7]:

| # | CPU action | Client status / effect | Server |
|---|---|---|---|
| 1 | out F880 ← 00; out F882 ← 01, then 02 | Pending disables. TA and RI are already 1. | — |
| 2 | poll F880 until `&0x81 == 0x81` | Passes immediately (0x91 or 0x81). | — |
| 3 | Build the TX page 0 (§4): RAM[1] = F5 (server), RAM[2] = F6, RAM[F6..FF] = `FF FF 00 03 nn 00 73 65 67 sel` | RAM[0] (SID) is **not written**. | — |
| 4 | out F882 ← **8C** | RX page 1, broadcast enabled, **RI = 0** | — |
| 5 | poll until `&0x80 == 0` | Passes immediately. | — |
| 6 | out F882 ← **03** | TX page 0, **TA = 0, TMA = 0** | — |
| 7 | (token reaches the client) | FBE → F5 | If the server's RI = 0, it sends ACK. If RI = 1, it sends NAK and the client retries at every rotation. |
| 8 | | The client sends the 10-byte packet, SID = FE. | Server RX page: [0] = FE, [1] = F5, [2] = F6, data at F6. It sends **ACK**, then sets **RI = 1** (interrupt if masked in). |
| 9 | poll `&0x01` (TA), then check `&0x03 == 3` | **TA = 1, TMA = 1**, so success. If TA = 1 and TMA = 0, the ROM issues `01`, `03` and resends, up to 20 times [ROM 04E7]. | `bootrec` reads the request, re-enables receive, and starts `bootsnd`. |
| 10 | Loop: check timer 1 (timeout 0x125C) and poll `&0x80` | Waiting. | `bootsnd` builds a reply block with **DID = 0** in its TX page and issues ENABLE TRANSMIT. At its token: broadcast. **No FBE, no ACK.** The server's TA = 1 and TMA = 0. |
| 11 | | If the client's RI = 0 and b = 1: copy to page 1 (D8400): [0] = F5, [1] = 00, [2] = COUNT, data. **RI = 1.** If the client's RI is still 1 (busy), the block is silently lost; the ROM's bitmap tolerates this. | |
| 12 | RI seen. Check SID (RAM[0] of page 1) == server node [ROM 0585]. The data starts at offset RAM[2]; check FF FF, 'b' and the selector, then copy the payload. | | |
| 13 | out F882 ← **8C** (re-arm, one packet per enable) [ROM 05E2] | RI = 0 | |
| … | Repeat from step 10 until the last block arrives and the bitmap is complete; then far-jump to the entry point. | | |

The ROM's parser reads only `RAM[2]` as the data offset, so the server's replies must be **short packets** (≤ 253 bytes). Each reply has a 30-byte header, so at most 223 payload bytes per block.

## 8. Ambiguities and gotchas

1. **SID on transmit** isn't specified. The ROM proves the chip inserts its own ID; **ignore TX buffer byte 0**.
2. **RECON definition.** The status-bit text says *"reconfiguration timer has timed out because the RX input was idle for 78.2 microseconds"*. The timer is 840 ms; 78.2 µs is the idle timer. Treat RECON as "a reconfiguration occurred". The ROM's interrupt self-test needs RECON = 1 a few ms after reset, and needs it to stay 0 right after `0x1E`.
3. **Timeout numbers disagree.** The text says 74.7 / 78.2 µs; Table 1 says 78 / 86 µs. Neither matters at emulation granularity.
4. **The default configuration after POR** (short-only vs. long) isn't stated, and the ROM never issues DEFINE CONFIGURATION. **Recommendation:** default to short-only. The QNX driver presumably issues 0x0D itself if it wants long packets; check its trace.
5. **The deferred disables** ("when the COM 9026 next receives the token") mean that on a lone node a DISABLE may never take effect. The ROM is only safe because TA and RI are already 1. Resolving them immediately when there's nothing to cancel is safe.
6. **Rewriting RAM on reconfiguration.** The flowchart's reconfiguration-timeout path goes through "READ ID FROM SWITCHES → WRITE ID TO RAM BUFFER". Whether it also rewrites D1 / RAM[0..1] on every 840 ms timeout isn't clear. **Recommendation:** write D1 and the ID only at reset release, so a lone node doesn't corrupt the TX page.
7. **NAK retries forever.** The ROM gives up only through its own TA timeout (20 tries × 16 × 65536 polls).
8. **Illegible flowchart text.** The diamonds after "SEND PACKET" and after "DID = 0" are unreadable in the scan. I read them as "WAS PACKET BROADCAST?" and "BROADCAST ENABLED?".
9. **The `[0x3e8]` loop count [ROM 1671].** The interrupt test loads its timeout from DS:03E8 with DS = D800. That is a *word* read straddling RAM byte 0x1F4 (0xF1 after the RAM test) and the **odd address D83E9**. The loop length (241 to 65521 polls) therefore depends on what odd addresses in the D8000 window return. Either way, the test works if RECON is already set by then.
10. **Unicast to a node whose receiver is disabled for broadcast:** the b bit affects only DID = 0, so a unicast is still accepted.
11. **"Less than 254 bytes"** for short packets fits COUNT ≥ 3, so N ≤ 253. Long packets go up to 508 bytes.
